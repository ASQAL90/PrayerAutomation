BUILD AKTIF · GAMBAR LOCK SCREEN ≠ AUTO-LOCK SESI

Snapshot → apply → restore

Alur source C# + Rust. Tes terisolasi dan readback flags tidak membuktikan gambar atau mode terlihat di Windows nyata.

Batas keselamatan

Fitur ini mengubah lock screen pengguna; bukan wallpaper desktop. Consent gambar tersimpan terpisah dari checkbox auto-lock. Build baru tidak mereset profil lama. Pada pemeriksaan ini, opsi Windows lama aktif dan aplikasi utama tidak dijalankan.

Jangan Run as administrator, memasukkan kredensial, mengubah policy, menjalankan helper, atau menghapus jurnal sebagai workaround. Manifest portable diperiksa sebagai asInvoker/uiAccess=false; hasil Windows target masih menunggu acceptance pengguna biasa.

API gambar dan mode adalah dua batas berbeda

Microsoft mendeskripsikan LockScreen.SetImageFileAsync sebagai API pengaturan gambar dari StorageFile.[1] OriginalImageFile hanya mengambil file dan dapat gagal bila gambar sebelumnya diatur melalui stream.[2]

Windows menyediakan pilihan Spotlight, Picture dan Slideshow melalui Settings Personalization.[3] Implementasi membaca/menulis indikator HKCU SlideshowEnabled dan RotatingLockScreenEnabled; sumber Microsoft yang diperiksa tidak menetapkannya sebagai public API pemulihan mode. Karena itu flags yang sama bukan bukti mode benar-benar aktif.

Personalization CSP / LockScreenImageUrl memiliki scope Device, bukan User.[4] Jalur C# ini tidak memakai HKLM/CSP/GPO, helper Python/EXE pihak ketiga, atau API desktop wallpaper sebagai fallback.

01 · GATE DAN RECOVERY

Consent, dukungan dan mode harus dapat diperiksa

  • Startup/recovery pending diselesaikan sebelum apply baru diizinkan.
  • Event baru berasal dari lima waktu wajib; Terbit dan Duha tidak masuk jalur.
  • Mode missing, malformed atau konflik menahan apply.
  • Pending/unknown bukan alasan elevate atau menghapus state.

Source: LockScreenImageScheduler.cs, LockScreenModeLogic, LockScreenSafetyProbe.cs.

↓mode awal dapat diidentifikasi
02 · SNAPSHOT DAN HASH

Siapkan pemulihan sebelum perubahan

  • PNG sementara disalin ke lokasi terkelola dan diverifikasi SHA256.
  • Picture: file asal harus lokal, terbaca, dapat disalin dan hash-nya cocok.
  • Spotlight/Slideshow: restore menyimpan mode; gambar/URI awal bukan syarat.
  • Build tidak membackup folder/options Slideshow.
  • Gambar sementara yang tidak memiliki jurnal valid tidak ditimpa begitu saja.

Source: WindowsLockScreenImageBackend.CaptureSnapshot.

↓jurnal lebih dahulu, setter kemudian
03 · JOURNAL BEFORE SETTER

Simpan snapshot persisten

Jurnal %LOCALAPPDATA%\PrayerAutomation\LockScreen\lock-screen-restore.json berisi mode awal, hash/path terkelola dan deadline UTC. Store memakai temporary file, Flush(true) dan rename sebelum native setter dipanggil.

Kegagalan penyimpanan menahan apply. Jurnal malformed dikarantina dan memblokir perubahan baru sampai ditinjau. Jangan menghapus jurnal/backup saat transaksi pending.

Source: FileLockScreenRestoreStore.Save, LockScreenImageTransaction.BeginOrExtendAsync.

↓pemeriksaan ulang ownership
04 · APPLY DAN READBACK

Terapkan gambar sementara

  1. Periksa ulang state, file dan ownership sebelum setter.
  2. Tunggu persiapan StorageFile; periksa ownership lagi tepat sebelum native write.
  3. Panggil LockScreen.SetImageFileAsync dan tunggu selesai sebelum rollback memeriksa efeknya.
  4. Verifikasi path/hash gambar sementara, set indikator Picture, lalu baca ulang.

Pemeriksaan ulang tidak membuat operasi atomik terhadap perubahan pengguna/Windows yang bersamaan. Readback internal bukan acceptance visual.

↓durasi tetap 60 menit dari event
05 · MONITOR DAN DEADLINE

Restore saat deadline, disable atau Exit

  • Durasi 60 menit adalah konfigurasi source, bukan deteksi selesai sholat.
  • Event baru ketika transaksi masih dimiliki dapat memperpanjang deadline.
  • Disable consent lewat Save meminta restore-only tanpa apply baru.
  • Exit menunggu operasi in-flight dan meminta restore; kegagalan dapat membuat app tetap hidup untuk retry.
  • Recovery memeriksa kembali dengan interval/backoff 30 detik ketika diperlukan.

Force-close berarti aplikasi tidak dapat memulihkan sampai dijalankan kembali. Jangan memanipulasi jam Windows atau membuat event sholat buatan pada profil harian.

Target pemulihan tiap mode

Spotlight

Kembali ke mode Windows Spotlight. Gambar Spotlight yang sama dan URI awal tidak disyaratkan.

Keberhasilan visual/mode nyata belum diterima.

Picture

Kembali ke gambar asal yang hash-nya diverifikasi dan ke mode Picture. Backup tidak valid harus menahan apply/restore yang tidak dapat dibuktikan.

Windows dapat tidak menyediakan file asal; jangan menggantinya dengan tebakan.

Slideshow

Kembali ke mode Slideshow. Build hanya menyimpan flags mode, bukan snapshot folder/options lengkap.

Folder/options dan slideshow berjalan perlu diperiksa pengguna.

Ter-verifikasi internal / override

Jika restore internal terverifikasi, transaksi dapat membersihkan state terkelolanya. Jika pengguna mengganti gambar/mode sendiri, ownership classifier harus mempertahankan override dan tidak memaksakan snapshot lama.

Hasil tersebut tetap dibedakan dari pengamatan lock screen yang terlihat.

Pending / kegagalan

Jurnal dipertahankan untuk recovery. Apply baru ditahan jika ownership/restore tidak dapat diverifikasi. Mode/path/hash dan penolakan native harus dilaporkan, bukan dibypass dengan elevation.

Force-close, invalid journal, file unreadable dan interleaving diuji secara sintetis; bukan fault injection terhadap profil asli.

Yang masih harus diuji pada Windows nyata

Gambar sementara terlihat, mode Spotlight/Picture/Slideshow benar-benar pulih, gambar Picture asal, folder/options Slideshow, restart/force-close/recovery dan override serentak masih menunggu acceptance. Tes ini mengubah pengaturan pengguna dan perlu persetujuan terpisah.

Ikuti checklist L01–L04 dan R01–R04. Win+L adalah tindakan manual pengguna; bukan bukti auto-lock scheduler. Unlock melalui login Windows biasa; jangan kirim PIN/password/kode.
